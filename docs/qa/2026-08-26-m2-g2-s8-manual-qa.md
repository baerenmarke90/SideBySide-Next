# M2/G2 S8 – manuelle Accessibility- und Privacy-Abnahme

**Issue:** #145  
**Status:** VORBEREITET – manuelle Durchführung offen  
**Ausgangsstand:** `main` `78fb496468eb81f0e8ca62b902f56b8a4d50380c`  
**Scope:** dünner S8-Referenzflow auf Web und Android  
**Gate-Regel:** G2 kann aus diesem Scope nur freigegeben werden, wenn kein Blocker-, kritischer oder hoher Accessibility-/Privacy-Befund offen ist.

Dieser Bericht ist die Arbeits- und Ergebnisvorlage für #145. Er ersetzt keine manuelle Prüfung. Ergebnisse werden erst nach tatsächlicher Durchführung eingetragen.

Verbindliche Grundlage ist `docs/ACCESSIBILITY-QA-MATRIX.md`. Für #145 wird bewusst nur der gelieferte S8-Kernflow geprüft:

`Anmeldung -> Memory anlegen -> Bild auswählen/hochladen -> Status/Fehler -> Timeline/Memory mit Bild -> Logout`

## 1. Testregeln

- ausschließlich synthetische Testdaten verwenden;
- keine realen privaten Bilder, Konten oder Inhalte verwenden;
- Web und Android gegen einen echten SideBySide-Stack testen;
- Android-Remotezugriff nur über HTTPS; die App erlaubt absichtlich kein Cleartext-HTTP;
- keine Teständerung vornehmen, die Privacy-, Netzwerk- oder Security-Grenzen lockert;
- Abweichungen mit Severity `Blocker`, `Kritisch`, `Hoch`, `Mittel` oder `Niedrig` dokumentieren;
- jeder offene mittlere/niedrige Befund benötigt ein eigenes Folge-Issue;
- Blocker/kritische/hohe Befunde müssen vor einem positiven G2-Ergebnis behoben und erneut geprüft werden.

## 3. Vorbereitung des synthetischen Teststands

Der reale G2-E2E-Harness in `.github/workflows/g2-e2e.yml` zeigt den erwarteten technischen Stack: API, Worker, PostgreSQL und LocalMediaStore. Für die manuelle Abnahme darf derselbe Self-Hosted-Stack oder eine gleichwertige isolierte HTTPS-Testumgebung verwendet werden.

Benötigt werden:

1. ein synthetischer Account mit Passwort-Anmeldung;
2. ein aktiver synthetischer Space dieses Accounts;
3. eine HTTPS-API-Basis-URL, die vom Android-Gerät erreichbar ist;
4. ein kleines synthetisches JPEG/PNG/WebP ohne reale private Inhalte.

### Web konfigurieren

Der Web-Referenzclient liest:

```text
VITE_SBS_API_BASE_URL=https://<qa-host>
VITE_SBS_SPACE_ID=<synthetische-space-id>
```

Lokale, nicht eingecheckte Konfiguration kann z. B. über `web/.env.local` gesetzt werden. Danach:

```bash
cd web
npm ci --ignore-scripts --no-audit --no-fund
npm run dev
```

### Android konfigurieren

Der Android-Referenzclient erhält API und Space beim Build:

```bash
cd android
gradle \
  -PsbsApiBaseUrl=https://<qa-host> \
  -PsbsSpaceId=<synthetische-space-id> \
  :app:assembleDebug
```

Der CI-Stand verwendet JDK 17, Gradle 9.5.0 und Android SDK 37.1. Das APK liegt anschließend unter dem normalen Gradle-Buildoutput von `android/app/build/outputs/apk/debug/`.

Die Android-Konfiguration darf für diese Abnahme **nicht** auf HTTP oder eine gelockerte Network-Security-Config umgestellt werden. `AndroidManifest.xml` setzt `allowBackup=false`, erlaubt nur `INTERNET` und `network_security_config.xml` verbietet Cleartext-Traffic.

## 4. Web – manueller Prüfablauf

### W1 – Ausgangszustand und Anmeldung

1. Browserstorage für die QA-Origin vor Testbeginn leeren.
2. Seite neu laden.
3. Ohne Maus nur mit `Tab`/`Shift+Tab` durch die Anmeldung navigieren.
4. Prüfen, dass E-Mail, Passwort und `Anmelden` in logischer Reihenfolge erreichbar sind.
5. Prüfen, dass der sichtbare Fokus eindeutig erkennbar ist.
6. Mit Screenreader prüfen: Überschrift `Anmelden`, Feldnamen, Rollen und `Anmelden` müssen verständlich angesagt werden.
7. Anmeldung absenden.
8. Während des Requests muss `Anmeldung läuft …` als Status verständlich wahrnehmbar sein.
9. Nach Erfolg muss `Authentifiziert` erscheinen und der S8-Inhalt ohne Fokusfalle erreichbar sein.

**Ergebnis:** _offen_  
**Severity/Befund:** _offen_

### W2 – Memory-Formular vollständig per Tastatur

1. Nur per Tastatur zu `Erinnerung festhalten` navigieren.
2. Titel ausfüllen.
3. Erinnerungstext ausfüllen.
4. optionales Datum setzen.
5. Dateiauswahl über Tastatur öffnen und ein synthetisches Bild auswählen.
6. Prüfen, dass alle Felder einen verständlichen Namen besitzen.
7. Prüfen, dass kein Pflichtschritt nur über Farbe oder Maus verständlich/bedienbar ist.
8. `Erinnerung mit Bild speichern` per Tastatur auslösen.
9. Loading-/Success-Status mit Screenreader prüfen.

**Ergebnis:** _offen_  
**Severity/Befund:** _offen_

### W3 – Ergebnis, Bild und Story

1. Nach erfolgreichem Speichern `Zuletzt gespeichert` prüfen.
2. Screenreader muss die Bereichsüberschrift, Memory-Titel/-Text und eine sinnvolle Bildbeschreibung erreichen.
3. `Gemeinsame Story` erreichen.
4. `Aktualisieren` per Tastatur auslösen.
5. Loading-, Content- und ggf. Error-Zustand auf verständliche Live-/Alert-Semantik prüfen.
6. Prüfen, dass die gespeicherte Erinnerung in der Story verständlich erscheint.

**Ergebnis:** _offen_  
**Severity/Befund:** _offen_

### W4 – 200 % Zoom und Layout

1. Browserzoom auf 200 % stellen.
2. kompletten S8-Flow mindestens einmal visuell durchgehen.
3. Prüfen: keine abgeschnittenen Pflichttexte, keine verdeckten Buttons/Felder, keine horizontale Scrollpflicht für die Kernaufgabe.
4. Fokus muss weiterhin sichtbar bleiben.
5. Status-/Fehlertexte dürfen nicht allein durch Layoutverlust verschwinden.

**Ergebnis:** _offen_  
**Severity/Befund:** _offen_

### W5 – Fehlerzustände

Mindestens diese Fehler manuell erzeugen:

1. falsches Passwort;
2. Speichern mit bewusst nicht erlaubtem oder fehlerhaftem Bild, soweit ohne Scope-Erweiterung reproduzierbar;
3. API kurzzeitig nicht erreichbar oder Request scheitert auf andere kontrollierte Weise.

Prüfen:

- Fehler ist textlich verständlich;
- Screenreader erkennt den Fehler;
- Fokus geht nicht verloren;
- vorherige Eingaben verschwinden nicht unnötig;
- keine technische Antwort verrät private Inhalte, Token oder signierte URLs.

**Ergebnis:** _offen_  
**Severity/Befund:** _offen_

### W6 – Logout und Privacy

1. nach erfolgreich geladenem Memory/Bild `Abmelden` per Tastatur auslösen;
2. prüfen, dass Ergebnisbild, Memory-Inhalt und Story aus der Oberfläche verschwinden;
3. Browser Developer Tools öffnen und mindestens `Local Storage`, `Session Storage`, IndexedDB und Cache Storage prüfen;
4. prüfen, dass dort kein Access-/Refresh-Token, keine Signed URL und kein privater Memory-/Bildinhalt aus dem S8-Slice persistiert wurde;
5. Seite nach Logout neu laden;
6. prüfen, dass kein alter authentifizierter S8-Inhalt wieder erscheint;
7. Browser-Zurück ausführen und erneut prüfen, dass kein privater Inhalt wieder sichtbar wird.

**Ergebnis:** _offen_  
**Severity/Befund:** _offen_

### A6 – Logout und Privacy

1. nach erfolgreichem Flow ausloggen.
2. prüfen, dass Memory-Ergebnis, Bildbytes, Story und Bildauswahl aus der sichtbaren Session verschwinden.
3. App über Recents verlassen und neu öffnen.
4. prüfen, dass keine alte Session automatisch wieder erscheint.
5. prüfen, dass die App kein Backup anbietet bzw. der Build `allowBackup=false` beibehält.
6. prüfen, dass der Photo Picker kein allgemeines Storage-Permission-Prompt ausgelöst hat.
7. prüfen, dass kein Share Sheet unerwartet für Bild/Read-URL geöffnet wurde.
8. auf dem Gerät keine persistente private Read-URL oder Datei aus dem S8-Slice erwarten; bei technisch nachvollziehbarem Befund als Privacy-Finding dokumentieren.
